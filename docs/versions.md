# Versions and observed tool behavior

Checked on 2026-09-25, macOS 26.6.2 (25G83), Apple silicon (arm64, 12 CPU, 18 GiB).
Pinned versions live in [`versions.env`](../versions.env) and are embedded into
the binary (`kona version`). Verbatim `--help` output is in
[`cli-surface.md`](cli-surface.md), regenerated by `hack/capture-cli.sh`.

| Tool | Version | Install | Notes |
|------|---------|---------|-------|
| Apple `container` | 1.4.1 (2026-09-09) | `brew install container` (homebrew-core formula) | Also ships as a signed .pkg on GitHub releases. 1.4.0 was never released. |
| krunkit | 1.3.2 (2026-07-03) | `brew tap libkrun/krun && brew install libkrun/krun/krunkit` | Pulls libkrun 1.19.5, libkrunfw 5.6.2, virglrenderer-krun 0.10.4e, molten-vk 1.4.2, gvproxy 0.8.9. |
| vmnet-helper | 0.13.0 (2026-08-02) | `brew tap nirs/vmnet-helper && brew install vmnet-helper` | On macOS 26 it needs **no root**. Binary at `$(brew --prefix vmnet-helper)/libexec/vmnet-helper`, not on `PATH`. |

Homebrew now requires trusting third-party taps (`brew trust <tap>` or
`brew trust --formula <tap>/<formula>`) before it will load their formulae.
`kona doctor` prints the trust command along with the install command.

## Deviations from the original task brief

These are places where observed behavior differs from the brief. Each one is flagged here and in the relevant doc.

1. **`container` is a Homebrew core formula**, not only a .pkg. The cask can
   therefore declare `depends_on formula: "container"`. No .pkg is ever
   auto-installed.
2. **`slp/krunkit` is deprecated.** krunkit's README says to remove it. The
   `slp/homebrew-krun` repo now redirects to `libkrun/homebrew-krun`, and the
   project moved to `github.com/libkrun/krunkit`. The old tap is stuck on
   krunkit 1.1.1. kona uses `libkrun/krun`, and `kona doctor` detects the old
   tap and prints the migration commands.
3. **Venus is always on in krunkit.** `src/context.rs` calls
   `krun_set_gpu_options2(VIRGLRENDERER_VENUS | VIRGLRENDERER_NO_VIRGL)`
   unconditionally. The `--device virtio-gpu,width=,height=` argument is
   parsed and then ignored ("currently not configured"). kona does not pass it.
4. **krunkit boots via EFI only.** `--bootloader` is ignored, and the first
   `virtio-blk` is the root disk. The GPU node image is therefore a raw disk
   with an EFI system partition, not a kernel + initrd pair.
5. **`container run --kernel <path>` exists** as a per-container override. kona
   uses it by default and never changes the system default kernel. That change
   is only available through the opt-in `kona kernel install --system`. See
   [kernel.md](kernel.md).
6. **There is no `container system kernel get`.** The current default kernel is
   the symlink
   `~/Library/Application Support/com.apple.container/kernels/default.kernel-arm64`.
   On this host it points to `vmlinux-6.18.35-197-debug`, the "Kata 3.32.0-debug"
   kernel that has been the default since container 1.3.0. Recording or
   restoring the default means reading or re-pointing that target through
   `container system kernel set --binary`.
7. **`container` has no static-IP flag.** `--network <name>,mac=XX,mtu=N`
   pins the MAC and MTU only. Node IPs are pinned by static MAC plus in-guest
   static addressing. See [networking.md](networking.md).
8. **Default container MTU is 1280.** It is set explicitly with `mtu=`.
9. **`container k8s` exists** (experimental plugin, 1.2+). It is a
   single-node kind-style cluster using `kindest/node`. It is useful prior art,
   since it proves that a systemd + containerd node boots on the default
   kernel. It has no multi-node, GPU, or CNI choice, so it does not replace
   kona. kona does not use kind images.
10. **`container machine`** (1.3+) is a persistent VM with a home mount. It was
   evaluated as a node primitive and rejected: it has no `--network`/MAC pinning
   and no port publishing, and it mounts `$HOME` by default. kona nodes are
   plain `container run -d` VMs.
